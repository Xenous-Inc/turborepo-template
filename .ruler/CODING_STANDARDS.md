# Coding Standards

Rules for code in this repo. Biome enforces some of them; the rest are checked in review.

## TypeScript

- Use `import type` for type-only imports (`verbatimModuleSyntax`).
- No enums. Use `as const` objects.
- Name enum-like `as const` objects in PascalCase and their entries in UPPER_CASE: `Theme.DARK`, not
  `THEME.Dark` or `Theme.dark`.
- Give the union type the same name as the object, so one import brings both:
  `type Theme = EnumItem<typeof Theme>`, with `EnumItem` from `@xenous/typescript/enum`.
- No non-null assertions.

## Environment variables

- Read config via `import { ENV } from 'varlock/env'`, never `process.env` (Biome `noProcessEnv`).
- Build-only config uses `import 'varlock/auto-load'`. Never put auto-load in `src/`: varlock is
  absent from prod images.

## Dependencies

- Shared dependency versions go through pnpm catalogs. Use `"catalog:"` or `"catalog:<name>"` in
  `package.json`.

## App boundaries

Apps never import values from each other. A type-only import is the one exception, used in
`apps/tanstack/orpc/index.ts` and `apps/next/orpc/index.ts`:

```ts
import type { AppRouter } from '../../server/src/routers';
```

It reaches server's source by relative path plus a `references` entry in the app's `tsconfig.json`,
so it needs no workspace dependency, and neither frontend's `package.json` lists `server`. That keeps
`turbo prune --scope=tanstack` from pulling `apps/server` and `packages/db` into the frontend build.
Keep it type-only: `import type` is erased before the bundler resolves it, so a value import would
work locally and fail only inside Docker.

## File layout

Component file layout in `apps/tanstack` and `apps/next`. `entities/`, `features/` and `widgets/`
are FSD *layers*; files never sit directly in a layer. Each layer contains slices, and each slice has
an `index.ts` barrel plus segment folders (`ui/`, `model/`, `lib/`, `api/`).

- Slice folders are kebab-case: `entities/user/`, `widgets/app-header/`, `shared/ui/not-found/`.
  The exported component keeps its PascalCase name (`AppHeader`).
- Component *files* stay PascalCase: `entities/user/ui/UserAvatar.tsx`,
  `widgets/app-header/ui/AppHeader.tsx`. Kebab-case applies to the slice folder, not the file. No
  folder-per-component within a segment.
- Reach for a slice through its barrel (`~/widgets/app-header`, `~/entities/user`), never a deep
  path into `ui/`.
- Within a slice, import relatively (`../lib/format`). Only cross-slice imports use the `~/` alias.
- `shared/ui/` uses the same slice shape (`not-found/index.ts` plus `not-found/ui/NotFound.tsx`),
  which also mirrors `packages/ui`.
- `packages/ui` is that shape in kebab-case, generated by `restructure.sh`:
  `components/button/ui/button.tsx` plus `index.ts`.

## React

- In components, separate logical groups (hooks, derived state, handlers, render) with blank lines.
- Component props use `type`, not `interface`. Extending is an intersection:
  `type StatTileProps = React.ComponentProps<'div'> & { … }`. Redefine an inherited field by `Omit`-ing
  it first, or the intersection makes it `never` without an error. shadcn's generated components
  inline their props instead and are left alone.
- Never render a link through Base UI's `Button` `render` prop, and never use `nativeButton={false}`
  to silence the warning that causes. [Base UI says](https://base-ui.com/react/components/button#rendering-links-as-buttons)
  links have their own semantics, and `nativeButton` is for elements like `div` that can take button
  semantics. Style the link directly, and keep `Button` for real buttons:
  ```tsx
  <Link to='/dashboard' className={cn(buttonVariants({ variant: 'outline', size: 'sm' }), 'hidden sm:inline-flex')}>
  ```
  `buttonVariants` comes from `@xenous/ui/components/button`; merge extra classes with `cn()`.
- `nativeButton` defaults to `true`, which is right whenever `render` produces a real `<button>`,
  including our own button components. Set `nativeButton={false}` only when `render` produces a
  non-button element like a `div`, so Base UI adds the button role and keyboard handling itself.
- An icon inside a `Button`, or inside a link styled with `buttonVariants`, needs `data-icon` set to
  the side it sits on. Icon-only buttons (`size='icon'`, `icon-sm`, …) need nothing.
  ```tsx
  <Button size='sm'>
      Visit site
      <IconExternalLink data-icon='inline-end' />
  </Button>
  ```

## Styling

- A Tailwind 4 CSS module needs `@reference` before `@apply` can resolve theme utilities. Use the
  alias, never a relative path, so the file still works after a move:
  ```css
  @reference '~/styles/globals.css';
  ```
  Never `@reference 'tailwindcss'`. That loads only Tailwind's default theme, so our colors fail the
  build with ``Cannot apply unknown utility class `text-foreground` ``.
- `apps/next` only: its Tailwind PostCSS plugin can't resolve `~/`, so use
  `@reference '@xenous/ui/globals.css'`, or a relative path for tokens only the app's own
  `globals.css` defines.

## i18n

- Message keys are random word triplets (`amber_socket_kite`), which is what Sherlock generates on
  extract and what Paraglide recommends: copy changes never force a rename. Semantic keys are fine
  where the key names a fixed slot rather than a piece of copy: `validators_*` and `common_meta_*`.

## Comments

- Keep them short. One or two lines is usually enough, three at most. Background, history and
  rejected options belong in the commit message or the PR, not the file.
- Comment the *why*, never the *what*. If the code already says it, delete the comment.
- Use plain English. Short, common words. No em-dashes, no rhetorical flourishes, no
  "deliberately", "precisely", "worth noting". Write like a colleague leaving a note, not like an
  essay.
